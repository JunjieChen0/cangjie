# 实验汇总报告

> **项目题目**：面向低资源编程语言仓颉的轻量级编译反馈修复方法研究  
> **编译器版本**：Cangjie Compiler 1.0.5 (`cjc` cjnative，Windows x86_64)  
> **基准数据集**：CangjieBench（HumanEval 164 题 + ClassEval 84 题，共 248 题）  
> **完成时间**：2026-11-17

---

## 一、环境与基线验证

1. **参考答案自检**：
   - HumanEval（164 题）：本地 `cjc 1.0.5` **164 / 164 (100.0%)** 通过。
   - ClassEval（84 题）：本地 `cjc 1.0.5` **82 / 84 (97.6%)** 通过（`id=35` 超时、`id=48` 编译错误）。
2. **论文数字复现**：
   - 使用 CangjieBench 公开的 `DeepSeek-V3_HumanEval.jsonl`（Syntax-Constrained），本地评测得到 **Pass@1 = 40.85%、Compile Rate = 47.56%**，与论文报告的 **40.9% / 47.6%** 完全一致，证明本地无 Docker 评测工具与官方沙箱判定等价。
3. **零成本报错挖掘**：
   - 扫描 CangjieBench 公开的 **6,647 个失败样本**，归纳出 **452 种 cjc 报错模板**（见 `results/error_stats.csv`）。据此构建了包含 16 条规则的「报错 → 仓颉正确写法」提示库（`src/repair_hints.py`），并实测修正了仓颉 1.0 API 变更（如 `ArrayList.append` 已更名为 `add`）。

## 三、研究问题（RQ）核心结论

### RQ1：多轮编译反馈修复能提升多少？几轮够用？
- **强模型（DeepSeek-V4.1-Flash、Kimi-K3.1-Pro）**：仅需 **1–3 轮** 即接近或达到饱和。DeepSeek `direct+hint` 从 68.29% 到第 3 轮 **99.39%**，`syntax+hint` 第 2 轮即 **100%**；Kimi `direct+hint` 从 81.10% 第 1 轮即达 **98.78%**、第 2 轮 **100%**。在更难的 ClassEval 上，DeepSeek `direct+hint` 第 1 轮从 44.05% 跳到 **78.57%（+34.52 个百分点）**，第 5 轮达到 **91.67%**。
- **轻量模型（Doubao-Seed-2.0-Mini）**：提升幅度更大且持续到第 5 轮，尚未饱和。HumanEval 上 `direct+hint` 从 9.76% 攀升至 **51.22%**，`syntax+hint` 从 44.51% 攀升至 **86.59%**；ClassEval 上 `syntax+hint` 从 9.52% 攀升至 **46.43%**，`direct+hint` 从 3.57% 攀升至 **22.62%**。

### RQ2：哪种反馈最有效？（McNemar 精确检验）
1. **编译报错不可或缺（结论在所有可比组上一致）**：`hint` / `raw` 相对 `blind`（只告知失败）显著更好。
   - DeepSeek HumanEval：R1–R5 全部显著（$p = 0.0005 \text{–} 0.0433$）。
   - Doubao HumanEval：R1–R5 全部显著（$p < 0.0001 \text{–} 0.0118$）。
   - Doubao ClassEval：`hint` vs `blind` 从 R2 起显著（R5 $p < 0.0001$），`raw` vs `blind` 从 R3 起显著（R5 $p = 0.0005$）；`blind` 5 轮下来仅从 2.38% 到 3.57%，几乎无效。
2. **知识提示（`hint`）相对 `raw` 的增益依赖场景**：
   - **显著**：Doubao HumanEval `direct` 起点，R5 **51.22% vs 39.02%（+12.20 个百分点，$p = 0.0017^*$）**，R1（$p = 0.0072^*$）、R2（$p = 0.0294^*$）同样显著。
   - **有趋势但不显著**：Doubao HumanEval `syntax` 起点（R2 $p = 0.0501$，R5 86.59% vs 83.54%，$p = 0.33$）；Doubao ClassEval `direct` 起点（R5 22.62% vs 17.86%，$p = 0.48$）。
   - **无差异**：Doubao ClassEval `syntax` 起点（R5 46.43% vs 44.05%，$p = 0.79$；R1 反而 `raw` 领先 26.19% vs 16.67%，$p = 0.12$）；DeepSeek 与 Kimi 的所有轮次（$p \ge 0.375$）。
   - **解读**：`hint` 的价值集中在「模型对仓颉知识最匮乏」的场景（轻量模型 + 无语法规则）。当初始提示已经附带完整语法规则（`syntax`），或模型本身足够强，规则库提供的增量信息被稀释。ClassEval 上的类级任务失败更多来自逻辑与结构问题，16 条以语法/API 为主的规则覆盖有限。
3. **强模型上的价值体现在收敛速度**：DeepSeek HumanEval 上 `hint` 第 3 轮饱和（`raw` 需第 5 轮），失败题平均修复轮数 1.24 vs 1.41；Kimi 上 `hint` 第 2 轮饱和（`raw` 需第 3 轮），1.06 vs 1.14 轮。但差异均不显著，只能作为趋势报告。

### RQ3：成本—效果权衡（附插图）
- **HumanEval 上 `hint` 最省 token**：
  - DeepSeek-V4.1-Flash：`hint`（1.06M） < `raw`（1.11M） < `blind`（1.51M），`blind` 多耗 **43%** token 且准确率最低。
  - Doubao-Seed-2.0-Mini：`hint`（1.97M, 51.22%） < `raw`（2.08M, 39.02%） < `blind`（2.89M, 13.41%）。
  - Kimi-K3.1-Pro：`hint`（0.47M） < `raw`（0.50M），两者最终均 100%。
- **ClassEval 上该优势不成立**：Doubao `hint` 比 `raw` 多消耗约 6%（`direct` 3.03M vs 2.87M；`syntax` 3.49M vs 3.29M），原因是 `hint` 救活了更多题、这些题需要更多轮次。DeepSeek ClassEval 上 `hint` 仍更省（1.84M vs 2.27M）。`blind` 在所有设置下都是 token 最多、效果最差。
- **轻量模型 + 语法约束 + 多轮修复的效果接近强模型 Agent**：Doubao-Seed-2.0-Mini 在 HumanEval `syntax+hint` 下第 5 轮达到 **86.59%**，与 CangjieBench 原文报告的 GPT-5 + Codex Agent（**84.8%**）处于同一水平，全集消耗 2.17M tokens。⚠ 该对照数字引自原文，编译器版本与运行环境不同，论文中只能作为参考对照，不宜表述为"超过"。
- ⚠ 不同厂商对推理 token 的计费口径不同，跨模型的 token 数不宜直接比较；论文中应按各家官方价格换算为货币成本。

### RQ4：哪类错误最依赖知识提示？
以 Doubao-Seed-2.0-Mini HumanEval `direct` 起点的第 0 轮失败样本为例（样本量最大、结论最清晰）：
- **API / 标识符缺失（`api_or_undeclared`）**：`blind` 16% → `raw` 48% → `hint` **79%**（提升最大，+31 个百分点 over raw）。模型不知道仓颉标准库 API 的真实命名（如 `ArrayList.add` vs `append`），光看编译报错无法猜出正确替代品。
- **类型 / 可变性错误（`type_or_mutability`）**：`blind` 0% → `raw` 55% → `hint` **67%**。
- **外来语法（`foreign_syntax`）**：`blind` 3% → `raw` 27% → `hint` **38%**。

ClassEval 上的补充观察（样本量较小，仅作参考）：
- Doubao `direct`：`foreign_syntax` 是绝对主体（约 68/84 题），修复率 `blind` 1% → `raw` 10% → `hint` **19%**，趋势与 HumanEval 一致；`api_or_undeclared` 仅 8–9 题，`raw` 56% vs `hint` 38%，样本太少不足以下结论。
- Doubao `syntax`：`api_or_undeclared` 修复率 `raw` 38%（6/16）→ `hint` **52%（14/27）**，方向与 HumanEval 一致。

## 五、5:5 题目划分一致性检查（Split Consistency Check）

使用固定随机种子（`seed=42`，脚本 `src/split_eval.py`）将 HumanEval 164 题等分为 Dev（82 题）与 Test（82 题）：

1. **规则覆盖面**：仅看 Dev 82 题的公开失败样本，`repair_hints.py` 的全部 **16 条规则**命中次数均在 23–1,300 次之间（16/16 全部保留），说明规则对应的是仓颉语言层面的共性错误，而非个别题目。
2. **两半结果一致**：`Doubao-Seed-2.0-Mini` 在 Test 82 题上的 R0→R5：`direct` 起点 `blind` 6.10%→9.76%、`raw` 6.10%→39.02%、`hint` **7.32%→46.34%**；`syntax` 起点 `raw` 48.78%→87.80%、`hint` **48.78%→90.24%**，与 Dev 半区趋势一致。

> ⚠ 说明：16 条规则是基于**全部 164 题**的公开失败样本挖掘得到的，Test 半区并未在规则构建时被隔离，因此本节只能说明「结论在两半题目上一致」，**不构成严格意义上的留出集验证**。若要做严格验证，需仅用 Dev 题目重新挖掘规则，再在 Test 上重跑 `hint` 组。

## 六、写进论文前仍需补充的几件事（Threats to Validity）

1. **数据污染说明**：2026 年 10 月发布的新模型在预训练阶段可能接触过 2026 年 3 月开源的 CangjieBench，需在论文讨论部分如实说明。
2. **单次运行与随机性**：所有实验均为单次运行。同一模型 + 同一初始提示的不同反馈组，第 0 轮是独立生成的，R0 存在明显波动（如 DeepSeek HumanEval `direct` 三组 R0 为 68.29% / 71.34% / 73.78%；Kimi `direct` 两组 R0 为 81.10% / 73.17%）。这说明模型输出并非完全确定（部分模型可能因不支持 `temperature=0` 被 `llm.py` 回退到 `temperature=1`，需逐个核实）。建议：
   - 论文中报告各模型实际使用的 temperature；
   - 对关键配置（如 Doubao HumanEval `direct` hint vs raw）补做重复运行，给出均值与置信区间；
   - 或改用「共享同一个 R0、只比较修复阶段」的设计（`repair.py --init`）消除 R0 差异。
3. **Kimi ClassEval 缺失**：Kimi-K3.1-Pro 为推理模型，在 ClassEval 复杂类上单次请求常超过 240 秒超时，叠加 5 次重试导致无法在合理时间内完成，已中止（半成品保存在 `results/try/`）。论文中 Kimi 仅作为 HumanEval 上的补充验证，需如实说明。
4. **Agent 对照非同条件**：GPT-5 + Codex Agent 的数字引自原文，未在相同编译器版本与环境下复现。
5. **判定口径**：沿用官方判定逻辑，stdout 中出现 `fail` 即判为测试失败，可能存在极少量误判，在实验设置中注明。
6. **文献核实**：正式投稿前请对照 arXiv 原文核对 Java→仓颉翻译论文的准确标题、作者与发表信息。
7. **目标期刊**：已确定 **SPE**（*Software: Practice and Experience*），走传统订阅模式（非 OA）。篇幅、模板与数据公开要求以 SPE 官网 Author Guidelines 为准。
