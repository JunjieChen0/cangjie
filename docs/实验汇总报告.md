# 实验汇总报告

> **项目题目**：面向低资源编程语言仓颉的轻量级编译反馈修复方法研究  
> **编译器版本**：Cangjie Compiler 1.0.5 (`cjc` cjnative，Windows x86_64)  
> **基准数据集**：CangjieBench（HumanEval 164 题 + ClassEval 84 题，共 248 题）  
> **完成时间**：2026-11-17

## 一、环境与基线验证

1. **参考答案自检**：
   - HumanEval（164 题）：本地 `cjc 1.0.5` **164 / 164 (100.0%)** 通过。
   - ClassEval（84 题）：本地 `cjc 1.0.5` **82 / 84 (97.6%)** 通过（`id=35` 超时、`id=48` 编译错误）。
2. **论文数字复现**：
   - 使用 CangjieBench 公开的 `DeepSeek-V3_HumanEval.jsonl`（Syntax-Constrained），本地评测得到 **Pass@1 = 40.85%、Compile Rate = 47.56%**，与论文报告的 **40.9% / 47.6%** 完全一致，证明本地无 Docker 评测工具与官方沙箱判定等价。
3. **零成本报错挖掘**：
   - 扫描 CangjieBench 公开的 **6,647 个失败样本**，归纳出 **452 种 cjc 报错模板**（见 `results/error_stats.csv`）。据此构建了包含 16 条规则的「报错 → 仓颉正确写法」提示库（`src/repair_hints.py`），并实测修正了仓颉 1.0 API 变更（如 `ArrayList.append` 已更名为 `add`）。
4. **ClassEval 全部测试复评工具验证**（`src/reeval_classeval.py`）：
   - CangjieBench 官方 ClassEval Pass@1 为 `pass_rate`（一道题的**全部测试**均通过），而非只看集成测试 `test[-1]` 的 `main_function_pass_rate`（官方结果表中 GPT-5 Syntax 23.8%、Codex Agent 32.1% 均为前者，后者分别为 36.9%、54.8%）。
   - 复评公开结果 `DeepSeek-V3` 与 `Kimi-K2` 的 Syntax-Constrained ClassEval：逐测试与官方 records **852/852 完全一致**，两种口径的通过数（8/9、10/15）与官方 summary 一致；官方参考答案全部测试通过 82/84。

## 三、研究问题（RQ）核心结论

### RQ1：多轮编译反馈修复能提升多少？几轮够用？
- **强模型（DeepSeek-V4.1-Flash、Kimi-K3.1-Pro）**：仅需 **1–3 轮** 即接近或达到饱和。DeepSeek `direct+hint` 从 68.29% 到第 3 轮 **99.39%**，`syntax+hint` 第 2 轮即 **100%**；Kimi `direct+hint` 从 81.10% 第 1 轮即达 **98.78%**、第 2 轮 **100%**。在更难的 ClassEval 上（全部测试口径），DeepSeek `direct+hint` 第 1 轮从 26.19% 跳到 **48.81%（+22.62 个百分点）**，之后增长放缓，第 5 轮 **54.76%**（`raw` 为 57.14%）。
- **轻量模型（Doubao-Seed-2.0-Mini）**：提升幅度更大且持续到第 5 轮，尚未饱和。HumanEval 上 `direct+hint` 从 9.76% 攀升至 **51.22%**，`syntax+hint` 从 44.51% 攀升至 **86.59%**；ClassEval 上（全部测试口径）`syntax+raw` 从 5.95% 攀升至 **27.38%**、`syntax+hint` 从 7.14% 攀升至 **25.00%**，`direct` 起点仅到 11.90%–13.10%。

### RQ2：哪种反馈最有效？（McNemar 精确检验）
1. **编译报错不可或缺（方向在所有可比组上一致）**：`hint` / `raw` 相对 `blind`（只告知失败）更好。
   - DeepSeek HumanEval：R1–R5 全部显著（$p = 0.0005 \text{–} 0.0433$）。
   - Doubao HumanEval：R1–R5 全部显著（$p < 0.0001 \text{–} 0.0118$）。
   - Doubao ClassEval（全部测试口径）：仅在 R5 显著，`hint` vs `blind` $p = 0.0078$、`raw` vs `blind` $p = 0.0039$（R1–R3 均不显著，绝对通过数很小）；`blind` 5 轮下来仅从 1.19% 到 2.38%，几乎无效。
2. **知识提示（`hint`）相对 `raw` 的增益依赖场景**：
   - **显著**：Doubao HumanEval `direct` 起点，R5 **51.22% vs 39.02%（+12.20 个百分点，$p = 0.0017^*$）**，R1（$p = 0.0072^*$）、R2（$p = 0.0294^*$）同样显著。该结论已由第六节三种补强设计（纯编译反馈、共享 R0 × 3 次重复）一致复现：共享 R0 三次重复合并 **+14.63 个百分点，95% CI [9.96, 19.72]**，每次重复均显著。
   - **有趋势但不显著**：Doubao HumanEval `syntax` 起点（R2 $p = 0.0501$，R5 86.59% vs 83.54%，$p = 0.33$）。
   - **无差异（ClassEval 全部测试口径下 `raw` 数值上反而略高）**：Doubao ClassEval `direct` 起点 R5 11.90% vs 13.10%（$p = 1.00$）；`syntax` 起点 R5 25.00% vs 27.38%（$p = 0.75$）；DeepSeek ClassEval R5 54.76% vs 57.14%（$p = 0.73$）。HumanEval 上 DeepSeek 与 Kimi 的所有轮次亦无差异（$p \ge 0.375$）。
   - 注：若按集成测试口径，Doubao ClassEval `direct` 曾呈现 `hint` 领先趋势（22.62% vs 17.86%，$p = 0.48$），复评后该趋势消失，说明 `hint` 多救活的题主要是「只通过集成测试」的部分正确代码。
   - **解读**：`hint` 的价值集中在「模型对仓颉知识最匮乏」的场景（轻量模型 + 无语法规则 + 函数级任务）。当初始提示已经附带完整语法规则（`syntax`），或模型本身足够强，规则库提供的增量信息被稀释。ClassEval 上的类级任务失败更多来自逻辑与结构问题，16 条以语法/API 为主的规则覆盖有限。
3. **强模型上的价值体现在收敛速度**：DeepSeek HumanEval 上 `hint` 第 3 轮饱和（`raw` 需第 5 轮），失败题平均修复轮数 1.24 vs 1.41；Kimi 上 `hint` 第 2 轮饱和（`raw` 需第 3 轮），1.06 vs 1.14 轮。但差异均不显著，只能作为趋势报告。

### RQ3：成本—效果权衡（附插图）
- **HumanEval 上 `hint` 最省 token**：
  - DeepSeek-V4.1-Flash：`hint`（1.06M） < `raw`（1.11M） < `blind`（1.51M），`blind` 多耗 **43%** token 且准确率最低。
  - Doubao-Seed-2.0-Mini：`hint`（1.97M, 51.22%） < `raw`（2.08M, 39.02%） < `blind`（2.89M, 13.41%）。
  - Kimi-K3.1-Pro：`hint`（0.47M） < `raw`（0.50M），两者最终均 100%。
- **ClassEval 上该优势不成立**：Doubao `hint` 比 `raw` 多消耗约 6%（`direct` 3.03M vs 2.87M；`syntax` 3.49M vs 3.29M），且全部测试口径下通过率并不更高。DeepSeek ClassEval 上 `hint` token 更少（1.84M vs 2.27M），通过率相近（54.76% vs 57.14%）。`blind` 在所有设置下都是 token 最多、效果最差。
- **ClassEval 与原论文同口径对比**（全部测试口径，非同条件）：DeepSeek-V4.1-Flash + 多轮修复达到 **54.76%–57.14%**，明显高于原文 GPT-5 + Syntax 一次生成（23.8%）与 GPT-5 + Codex Agent（32.1%）；Doubao-Seed-2.0-Mini + Syntax + 多轮修复为 **25.00%–27.38%**，与 GPT-5 一次生成处于同一水平。
- **轻量模型 + 语法约束 + 多轮修复的效果接近强模型 Agent**：Doubao-Seed-2.0-Mini 在 HumanEval `syntax+hint` 下第 5 轮达到 **86.59%**，与 CangjieBench 原文报告的 GPT-5 + Codex Agent（**84.8%**）处于同一水平，全集消耗 2.17M tokens。⚠ 该对照数字引自原文，编译器版本与运行环境不同，论文中只能作为参考对照，不宜表述为"超过"。
- ⚠ 不同厂商对推理 token 的计费口径不同，跨模型的 token 数不宜直接比较；论文中应按各家官方价格换算为货币成本。

### RQ4：哪类错误最依赖知识提示？
以 Doubao-Seed-2.0-Mini HumanEval `direct` 起点的第 0 轮失败样本为例（样本量最大、结论最清晰）：
- **API / 标识符缺失（`api_or_undeclared`）**：`blind` 16% → `raw` 48% → `hint` **79%**（提升最大，+31 个百分点 over raw）。模型不知道仓颉标准库 API 的真实命名（如 `ArrayList.add` vs `append`），光看编译报错无法猜出正确替代品。
- **类型 / 可变性错误（`type_or_mutability`）**：`blind` 0% → `raw` 55% → `hint` **67%**。
- **外来语法（`foreign_syntax`）**：`blind` 3% → `raw` 27% → `hint` **38%**。

ClassEval 上的补充观察（样本量较小，且此处「修复成功」按**集成测试口径**统计，仅作参考）：
- Doubao `direct`：`foreign_syntax` 是绝对主体（约 68/84 题），修复率 `blind` 1% → `raw` 10% → `hint` **19%**，趋势与 HumanEval 一致；`api_or_undeclared` 仅 8–9 题，`raw` 56% vs `hint` 38%，样本太少不足以下结论。
- Doubao `syntax`：`api_or_undeclared` 修复率 `raw` 38%（6/16）→ `hint` **52%（14/27）**，方向与 HumanEval 一致。

## 五、5:5 题目划分一致性检查（Split Consistency Check）

使用固定随机种子（`seed=42`，脚本 `src/split_eval.py`）将 HumanEval 164 题等分为 Dev（82 题）与 Test（82 题）：

1. **规则覆盖面**：仅看 Dev 82 题的公开失败样本，`repair_hints.py` 的全部 **16 条规则**命中次数均在 23–1,300 次之间（16/16 全部保留），说明规则对应的是仓颉语言层面的共性错误，而非个别题目。
2. **两半结果一致**：`Doubao-Seed-2.0-Mini` 在 Test 82 题上的 R0→R5：`direct` 起点 `blind` 6.10%→9.76%、`raw` 6.10%→39.02%、`hint` **7.32%→46.34%**；`syntax` 起点 `raw` 48.78%→87.80%、`hint` **48.78%→90.24%**，与 Dev 半区趋势一致。

> ⚠ 说明：16 条规则是基于**全部 164 题**的公开失败样本挖掘得到的，Test 半区并未在规则构建时被隔离，因此本节只能说明「结论在两半题目上一致」，**不构成严格意义上的留出集验证**。若要做严格验证，需仅用 Dev 题目重新挖掘规则，再在 Test 上重跑 `hint` 组。

## 六、补强实验（Doubao-Seed-2.0-Mini，HumanEval，`direct` 起点，N = 164，9 组，零异常）

为回应三类潜在质疑（测试信息泄漏、对照组过弱、单次运行与 R0 波动），在 `hint` 显著的主线配置上补做 9 组实验（原始结果见 `results/ablation/`）。

### 6.1 纯编译反馈消融（零测试泄漏）
`repair.py --compile-only-feedback`：修复阶段只编译 solution 本身（不拼接、不运行任何测试代码），编译通过即停止并做最终评测；模型在修复中接触不到任何测试信息。

| 组别 | R0 | R1 | R2 | R3 | R4 | R5 | 总 Token |
|---|---:|---:|---:|---:|---:|---:|---:|
| 纯编译 `hint` | 8.54% | 18.29% | 28.66% | **41.46%** | **46.34%** | **50.00%** | **1,768,630** |
| 纯编译 `raw` | 9.15% | 17.07% | 19.51% | 25.00% | 28.66% | 32.93% | 1,980,520 |
| （对照）原实验 `hint`（含测试输出） | 9.76% | 25.00% | 32.93% | 39.02% | 45.12% | 51.22% | 1,974,203 |
| （对照）原实验 `raw`（含测试输出） | 9.15% | 17.07% | 25.00% | 31.71% | 34.76% | 39.02% | 2,075,141 |

- McNemar（纯编译 `hint` vs `raw`）：R1 $p = 0.79$；R2 $p = 0.0059^*$；R3–R5 均 $p < 0.0001^*$（R5：37 vs 9）。
- 去掉测试输出后，`hint` 几乎不变（51.22% → 50.00%），`raw` 下降约 6 个百分点（39.02% → 32.93%），两者差距由 12.20 扩大到 **17.07 个百分点**：`hint` 的收益来自仓颉知识而非测试信息。
- 最终失败中，纯编译 `hint` 仍编译失败 65 题、测试失败 16 题；`raw` 分别为 99 题、11 题——`hint` 主要减少编译错误，与 RQ4 一致。

### 6.2 独立重采样基线（`pass@6`）
`src/sample_passk.py`：每题独立生成 6 次（`temperature = 0.8`），任一通过即算通过。

- 无偏 pass@k（k = 1…6）：6.81% / 9.92% / 12.20% / 13.98% / 15.55% / **17.07%**；总 Token **2,651,142**。
- 与 `blind`（13.41%）无显著差异（$p = 0.31$），说明「多试几次」与「只告诉模型错了」同样低效。
- 所有带报错反馈的修复组均显著优于 pass@6（$p < 0.0001$，如共享 R0 `hint` rep1：67 vs 1），且 token 更少（修复 1.48M–2.08M vs 重采样 2.65M）。
- 注：修复组通过即停止，平均调用次数少于 6 次，而 pass@6 每题固定 6 次调用，比较对修复组更严苛。

### 6.3 共享 R0 × 3 次重复
`repair.py --init results/ablation/doubao_mini_r0_init.jsonl --temperature 0.3`：所有组从同一份第 0 轮代码出发（即原 `hint` 实验第 0 轮生成的代码，164/164 一致；第 0 轮生成与反馈模式无关），只比较修复阶段。6 个文件的 R0 逐题一致（16/164 = 9.76%）。

| 组别 | 重复 | R0 | R1 | R2 | R3 | R4 | R5 | 修复阶段 Token |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| `hint` | rep1 | 9.76% | 23.78% | 32.32% | 41.46% | 51.22% | **57.32%** | 1,481,936 |
| `hint` | rep2 | 9.76% | 25.00% | 34.15% | 41.46% | 51.22% | **54.88%** | 1,481,105 |
| `hint` | rep3 | 9.76% | 24.39% | 32.32% | 41.46% | 48.78% | **54.88%** | 1,503,460 |
| `raw` | rep1 | 9.76% | 22.56% | 28.66% | 32.32% | 35.98% | 42.07% | 1,573,362 |
| `raw` | rep2 | 9.76% | 19.51% | 26.83% | 33.54% | 36.59% | 39.02% | 1,574,089 |
| `raw` | rep3 | 9.76% | 19.51% | 27.44% | 35.37% | 38.41% | 42.07% | 1,560,800 |

- **R5 均值 ± 标准差**：`hint` **55.69% ± 1.41%**，`raw` **41.05% ± 1.76%**；修复阶段平均 Token `hint` 1.49M < `raw` 1.57M。
- **逐次 McNemar（R5）**：rep1 30 vs 5（$p < 0.0001$）；rep2 32 vs 6（$p < 0.0001$）；rep3 31 vs 10（$p = 0.0015$）。
- **三次合并**：逐题平均通过率之差 **+14.63 个百分点，95% bootstrap CI [9.96, 19.72]**（按题目重采样 10,000 次）。
- 差距在后几轮拉开（R1 差异较小，R3 起稳定显著），说明 `hint` 帮助的是持续修复，而不只是第一处错误。

### 6.4 适用范围
以上补强实验全部基于「轻量模型 + 函数级任务 + 无语法规则（`direct`）」这一配置，支撑的结论是：**在该场景下，知识提示相对原始报错有稳定、显著的增益，且该增益不依赖测试信息、不是「多试几次」的效果**。在 ClassEval（全部测试口径）、`syntax` 起点以及强模型上，`hint` 相对 `raw` 均无显著优势（见 RQ2），论文主线须据此限定适用范围。

## 七、写进论文前仍需补充的几件事（Threats to Validity）

1. **数据污染说明**：2026 年 10 月发布的新模型在预训练阶段可能接触过 2026 年 3 月开源的 CangjieBench，需在论文讨论部分如实说明。
2. **单次运行与随机性（部分已缓解）**：第二节的 18 组主实验均为单次运行，同一模型 + 同一初始提示的不同反馈组第 0 轮独立生成，R0 存在波动（如 DeepSeek HumanEval `direct` 三组 R0 为 68.29% / 71.34% / 73.78%；Kimi `direct` 两组 R0 为 81.10% / 73.17%）。
   - 温度已核实（见第二节参数表）：Kimi-K3.1-Pro 的 API 拒收 `temperature=0`（`results/try/kimik31p_pilot.jsonl` 中的报错为 `temperature only 1 is allowed for this model`），`llm.py` 的回退逻辑即为此加入，Kimi 两组实际为 `temperature=1`，其 R0 波动与 hint/raw 差距不宜过度解读。DeepSeek 与 Doubao 主实验均在加入回退前跑完（或同一模型此前已稳定接受 0），且全部 `errors = 0`，实际为 `temperature=0`。注意 `llm.py` 的回退不写日志，以上结论依据 pilot 报错与时间线推断；后续实验应把实际温度写入记录。
   - 已缓解：核心配置（Doubao HumanEval `direct` hint vs raw）已用共享 R0 × 3 次重复验证（第六节）。其他配置仍为单次运行，结论按描述性结果报告。
   - 共享 R0 通过 `--init` 把第 0 轮代码重新拼成一条助手消息（而非保存原始对话），两组处理方式相同，比较是公平的，但与原生多轮对话略有差异，需在方法部分说明。
   - 温度设置不统一：主实验 0（Kimi 为 1）、共享 R0 重复 0.3、pass@6 为 0.8，需在论文中逐一写明。
3. **Kimi ClassEval 缺失**：Kimi-K3.1-Pro 为推理模型，在 ClassEval 复杂类上单次请求常超过 240 秒超时，叠加 5 次重试导致无法在合理时间内完成，已中止（半成品保存在 `results/try/`）。论文中 Kimi 仅作为 HumanEval 上的补充验证，需如实说明。
4. **ClassEval 修复只以集成测试为反馈和停止条件**：修复实验中 ClassEval 只拼接 `test[-1]` 编译运行，反馈与「通过即停止」都只看集成测试。复评显示，7 组中最终通过集成测试的 268 份代码里有 **107 份（39.9%）未通过方法级测试**。因此报告的全部测试口径结果是「仅按集成测试修复」时的水平，低于「按全部测试驱动修复」可能达到的上限。后续 ClassEval 修复实验应以全部测试作为反馈与停止条件（需修改 `repair.py`）。这一现象本身可作为 lessons learned：修复所依赖的测试信号决定最终质量。
5. **个别题目耗时处于超时边界**：ClassEval id=35 的官方参考答案在本机运行 10 秒超时；DeepSeek `direct+hint` 中该题修复时通过、复评时超时（机器负载不同），复评按未通过计，影响 1 题（约 1.2 个百分点）。
6. **Agent 对照非同条件**：GPT-5 + Codex Agent 的数字引自原文，未在相同编译器版本与环境下复现。
7. **判定口径**：沿用官方判定逻辑，stdout 中出现 `fail` 即判为测试失败，可能存在极少量误判，在实验设置中注明。
