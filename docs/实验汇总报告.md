# 实验汇总报告

> **项目题目**：面向低资源编程语言仓颉的轻量级编译反馈修复方法研究  
> **编译器版本**：Cangjie Compiler 1.0.5 (`cjc` cjnative，Windows x86_64)  
> **基准数据集**：CangjieBench（HumanEval 164 题 + ClassEval 84 题，共 248 题）  
> **更新时间**：2026-11-18（已纳入第 3 阶段全部 116 组可控重复实验数据，以及新题集 Original-30 的 59 组实验，见 RQ5）

## 一、环境与基线验证

1. **参考答案自检**：
   - HumanEval（164 题）：本地 `cjc 1.0.5` **164 / 164 (100.0%)** 通过。
   - ClassEval（84 题）：本地 `cjc 1.0.5` **82 / 84 (97.6%)** 通过（`id=35` 超时、`id=48` 编译错误）。
2. **论文数字复现**：
   - 使用 CangjieBench 公开的 `DeepSeek-V3_HumanEval.jsonl`（Syntax-Constrained），本地评测得到 **Pass@1 = 40.85%、Compile Rate = 47.56%**，与论文报告的 **40.9% / 47.6%** 完全一致，证明本地无 Docker 评测工具与官方沙箱判定等价。
3. **零成本报错挖掘与检索库**：
   - 扫描 CangjieBench 公开的 **6,647 个失败样本**，归纳出 **452 种 cjc 报错模板**（见 `results/error_stats.csv`）。据此构建了包含 16 条规则的「报错 → 仓颉正确写法」提示库（`src/repair_hints.py`）以及按报错动态检索语法/API 片段的 `rag` 策略，并实测修正了仓颉 1.0 API 变更（如 `ArrayList.append` 已更名为 `add`）。
4. **ClassEval 全部测试复评工具验证**（`src/reeval_classeval.py`）：
   - CangjieBench 官方 ClassEval Pass@1 为 `pass_rate`（一道题的**全部测试**均通过），而非只看集成测试 `test[-1]` 的 `main_function_pass_rate`。
   - 复评公开结果 `DeepSeek-V3` 与 `Kimi-K2` 的 Syntax-Constrained ClassEval：逐测试与官方 records **852/852 完全一致**，官方参考答案全部测试通过 82/84。

## 二、第 3 阶段全量实验总表（116 组可控实验，共 15,904 题次）

第 3 阶段采用**统一可控协议**（原始结果见 `results/stage3/`）：
- 同一「模型 × 数据集 × 初始提示」组合仅生成一次**共享第 0 轮代码**（9 组 R0），所有反馈组与重复均从该第 0 轮出发修复 0–5 轮；
- `DeepSeek-V4.1-Flash`（`deepseek-v4-1-flash-261017`）与 `Doubao-Seed-2.0-Mini`（`doubao-seed-2-0-mini-260428`）均使用 `temperature = 0.3`，每组重复 **3 次**；
- `Kimi-K3.1-Pro`（`kimi-k3-1-pro-261024`）受 API 限制使用 `temperature = 1.0`，HumanEval 重复 3 次、ClassEval 运行 1 次；
- **ClassEval 全部改为全测试驱动**：每一轮均编译运行全部测试，全部通过才停止；
- **Kimi 超时处理口径**：按实际生产可用性口径，单次请求超时（HumanEval 240 秒、ClassEval 600 秒）且重试耗尽后计为 `APITimeoutError`，不补跑，算未通过并保留在分母 164 / 84 中；Doubao（58 组）与 DeepSeek（48 组）全部 **`errors = 0`**。
- **统计口径**（`src/stage3_stats.py`，完整输出见 `results/stats/stage3_stats.md`）：先按题对 3 次重复求平均通过率，再求两组之差；95% CI 为按题 bootstrap（10,000 次）；p 为按题符号翻转置换检验（10,000 次）；全部 33 个比较一起做 Holm 校正，**显著以 p(Holm) < 0.05 为准**。逐次重复的 McNemar 只作稳健性参考。

## 三、研究问题（RQ）核心结论（基于第 3 阶段 3 次重复合并分析）

以下均基于三次重复合并后的逐题平均差值、**95% Bootstrap 置信区间**（按题目重采样 10,000 次）及各次重复的 **McNemar 精确检验**：

### RQ1：多轮编译反馈修复能提升多少？几轮够用？
- **强模型（DeepSeek-V4.1-Flash、Kimi-K3.1-Pro）**：HumanEval 上 **1–3 轮** 即达 99%–100% 饱和；在全测试驱动的 ClassEval 上，DeepSeek `direct` 从 25.00% 在第 1 轮跳升至 **51.19%–53.17%**，第 5 轮最高达 **72.22%**（`rag`）。作为参考，第 2 阶段“仅集成测试驱动修复再复评”为 54.76%–57.14%；两阶段的温度（0 与 0.3）、第 0 轮（各组独立生成与共享）和修复口径都不同，不是同条件比较，差距不能全部归因于全测试驱动；Kimi ClassEval 第 5 轮达到 **78.57%–82.14%**（已包含超时失败题）。
- **轻量模型（Doubao-Seed-2.0-Mini）**：提升幅度大且持续到第 5 轮。HumanEval `direct+hint` 从 10.98% 升至 **51.63% ± 1.86%**，`syntax+rag` 从 48.78% 升至 **88.01% ± 1.26%**；ClassEval `syntax+rag` 从 4.76% 升至 **35.31% ± 1.37%**（高于原论文 GPT-5+Syntax 一次生成 23.8% 及 Agent 32.1% 的报告值，非同条件对照）。

  1. **报错信息本身最关键**：`raw` 相对 `blind` 在 Doubao HumanEval 两种起点（+21.75、+15.85）和 DeepSeek ClassEval（+25.40）上显著，是全部比较中差值最大的。其余 `raw` vs `blind` 方向一致但不显著（DeepSeek HumanEval 已接近饱和；Doubao ClassEval `direct` 起点通过率过低）。
  2. **静态规则 `hint`**：只在「轻量模型 + 无语法规则（`direct`）+ 函数级任务」上显著优于 `raw`（+15.85，不给测试信息时 +14.43）。在 `syntax` 起点、ClassEval 和强模型上都无差异。
  3. **动态检索 `rag`**：在 Doubao HumanEval `direct` 起点与 `hint` 相当（均显著优于 `raw`）；在 **Doubao ClassEval 上显著优于 `raw`**（`direct` +8.73、`syntax` +7.94），是 ClassEval 上唯一显著优于 `raw` 的反馈方式。`rag` 优于 `hint`（Doubao HE `syntax` 与 CE，+4.27 至 +6.75）只是趋势，校正后不显著。在强模型 DeepSeek 的 ClassEval 上，`rag` 相对 `raw` 方向为正（+3.97），但不显著。
  4. **适用范围**：`hint` 与 `rag` 的增益都只在轻量模型上显著；强模型上只有“给报错优于不给”这一点在 ClassEval 上显著。`rag` 在 ClassEval 上的优势是第 2 阶段加入 `rag` 后才观察到的，属于探索性发现（见第七节）。
- **敏感性分析**：去掉判定不稳定的题（HumanEval 第 20 题、ClassEval 第 58 题），并在每个比较中去掉任一组超时的题后，全部 33 个比较的显著与否均不变；Doubao CE `direct` `rag` vs `raw` 的 p(Holm) 由 0.0052 变为 0.0208，仍显著。

### RQ3：成本—效果与纯编译反馈权衡
- **Token 开销分化**：
  - `hint` 在几乎所有配置下都比 `raw` 更省（或持平）修复阶段 Token（例如 Doubao HE `direct` 1.65M vs 1.72M；DeepSeek HE `direct` 0.27M vs 0.31M，CE `direct` 4.39M vs 4.58M）；
  - `rag` 因每轮附加检索到的文档片段，**在 Doubao 上比 `hint`/`raw` 多消耗约 17%–68% 的 Token**（如 Doubao HE `direct` 2.76M vs `hint` 1.65M；CE `syntax` 3.87M vs `hint` 3.40M）；但在高 R0 强模型（DeepSeek HE `syntax` 0.20M、CE `direct` 4.46M）上因轮数少，Token 反而不高。
- **零测试泄漏纯编译消融（C 组，18 组）**：
  - 去掉所有测试反馈后，`Doubao` `hint_co` 仍达 **47.97%**（对比含测试 `51.63%`，仅差 3.66 pp），`DeepSeek` 达 **94.51%–94.71%**（对比含测试 `99.80%`，差约 5 pp，即能编译通过但逻辑未通过测试、又拿不到测试反馈的题）。以 R0 为起点计算，不给测试信息时保留的修复收益，Doubao `hint` 约为 91%（+36.99 / +40.65 pp），DeepSeek 约为 79%（+19.71 / +24.80 pp）：大部分收益来自 `cjc` 编译报错与领域知识，而不是测试信息；强模型剩下的失败更多是逻辑错误，需要测试反馈。
- ⚠ 不同厂商的推理 Token 计费口径不同，论文中跨模型成本对比应按各家官方单价换算为货币成本。

## 七、有效性威胁与数据质量说明（Threats to Validity）

1. **数据污染说明**：2026 年 10 月发布的新模型在预训练阶段可能接触过 2026 年 3 月开源的 CangjieBench，需在论文讨论部分如实说明。为此补做了新题集 Original-30（RQ5）：轻量模型上 `raw` vs `blind` 与 `hint` vs `raw` 两条主要结论在新题上仍显著。局限是只有 30 道函数级题、没有类级新题，强模型修复后接近 100%（天花板效应），`rag` 的效果在新题上未能确认。
2. **Kimi-K3.1-Pro 超时与参数差异**：
   - API 强制要求 `temperature = 1.0`（无法设 0.3）；
   - 关闭 SDK 双重重试（`max_retries=0`）后，Kimi 在复杂长推理题上仍会超时（单次请求上限 HumanEval 240 秒、ClassEval 600 秒）：HE `raw` 每组 1–2 题、`hint_rep2` 1 题；CE `raw` 11 题、`hint` 7 题，均为 `APITimeoutError`。按生产实际口径，超时题不补跑，记为未通过并保留在 164 / 84 分母中；Doubao 与 DeepSeek 仍要求 `errors = 0`，出错即补跑。
   - 影响：(a) 两组超时数不同会让组间比较产生偏差（如 Kimi HE `raw` 4 题次、`hint` 1 题次，主分析中 `hint` 比 `raw` 高 +0.61，去掉超时题后为 0.00），敏感性分析已去掉任一组超时的题，结论不变；(b) Kimi 的通过率是下限估计，与补跑到无错误的 DeepSeek 不完全可比，跨模型比较时应写成“至少 X%”；(c) 超时请求的 token 没有记录，Kimi 的成本略被低估；(d) Kimi ClassEval 只运行 1 次，超时题最多约占 13%，去掉超时题后只剩 71 题，只作参考，不作为主要证据；(e) Original-30 上 Kimi 只有 1 题次超时（`hint_rep2` 第 1022 题），`hint` vs `raw` 的 −1.11 完全来自这一题。
3. **判定不稳定的题**（参考答案重复编译运行检查：HumanEval 每题 5 次，ClassEval 每题每个测试 3 次）：
   - **HumanEval 第 20 题**：官方测试用 `!=` 比较 `(Float64, Float64)` 元组，`cjc 1.0.5` 时而接受、时而报“不支持”（约一半），属于编译器本身的不确定性，与模型代码无关。这导致 `ds_v41f_he_syntax_hint_rep1..3`、`rag_rep1` 与 Kimi HE `rep2` 两组的第 0 轮判定与共享文件不一致（R0 显示 89.02% vs 89.63%）。
   - **ClassEval 第 58 题**（扫雷）：参考答案随机布雷、可能落在同一格，检查雷数的方法级测试约 1/10 不通过。
   - 另外，ClassEval 第 12 题在第 3 阶段的约 3.5 万次判定中出现过 1 次同一代码判为运行异常；Kimi HE 共享第 0 轮中第 143 题判为运行超时，修复组中均判为通过，推测与当时机器负载有关。两组受影响程度相同，不会让比较偏向任何一方。
   - 敏感性分析去掉第 20、58 题后，全部结论不变（见 RQ2）。所有原始文件均未删改。
4. **探索性结论与多重比较**：`rag` 是第 2 阶段才加入的，“`rag` 在 ClassEval 上有效”是看到第 2 阶段数据后才形成的假设，第 3 阶段虽在新的可控协议下验证，仍应作为探索性发现报告。第 3 阶段共 33 个比较，统一做了 Holm 校正；未校正 p < 0.05 但校正后不显著的比较（RQ2 表中 ◐）只能写成趋势。
5. **共享 R0 的对话构造方式**：通过 `--init` 将第 0 轮代码拼为一条助手消息后再续修，所有对比组处理完全一致、保证组间公平，但与原生单次连续多轮会话略有差异。
6. **Agent 对照非同条件**：GPT-5 + Codex Agent 的数字引自原文，编译器版本与运行环境不同。
7. **判定口径与边界超时**：沿用官方判定逻辑，stdout 出现 `fail` 即判为测试失败；ClassEval `id=35` 处于本机 10 秒运行超时边界，高并发下可能受机器负载影响。
8. **投稿规范与 AI 披露**：目标期刊为 **SPE**（*Software: Practice and Experience*，非 OA）。若投稿要求披露生成式 AI 工具使用，需在致谢或方法声明中如实说明并由人类作者对全部数据与结论负全责。
