# 第 3 阶段实验清单（给运行实验的作者）

## 一、这一阶段要跑什么

统一协议如下：

- temperature 为 0.3，每组重复 3 次（Kimi 的 API 只允许 1）。
- 同一（模型 × 数据集 × 初始提示）组合只生成一次第 0 轮代码，所有反馈组和重复都从这份代码开始修复。
- 最多修复 5 轮。ClassEval 每一轮都跑全部测试，全部通过才停止。

| 组 | 内容 | 修复运行数 |
|---|---|---|
| A | HumanEval：{DeepSeek, Doubao} × {direct, syntax} × {blind, raw, hint, rag} × 3 次 | 48 |
| B | ClassEval 全部测试驱动：{DeepSeek, Doubao} × direct × 4 种反馈 × 3 次（DeepSeek 超时放宽到 600 秒）；Doubao syntax × {raw, hint, rag} × 3 次 | 33 |
| C | 只给编译错误：{DeepSeek, Doubao} × direct × {raw, hint, rag} × 3 次 | 18 |
| D | Kimi（T=1）：HumanEval direct × {raw, hint} × 3 次；ClassEval direct × {raw, hint} × 1 次（超时放宽到 600 秒） | 8 |

另外还要生成 9 份共享的第 0 轮代码。全部运行由 `src/run_matrix.py` 自动完成，结果写在 `results/stage3/`，不会覆盖旧实验。

按官方单价折算，总成本约 600 元（DeepSeek 约 350 元，Kimi 约 200 元，Doubao 约 60 元）。实际是通过 Coding Plan 订阅调用的。

## 二、开跑前检查（约 5 分钟）

1. **查套餐额度**：在火山方舟控制台查看 Coding Plan 的请求额度，比如每 5 小时能调用多少次。本阶段约有 107 组 × 164 题 × 平均 2–3 次调用，额度不够会中途限流。如果额度不够，先联系项目负责人，决定是升级套餐还是改用按量计费的 API Key。
2. **确认 `.env` 已配置**：`LLM_BASE_URL` 和 `LLM_API_KEY` 都要填好。模型名由脚本自动传入，不需要改 `LLM_MODEL`。
3. **代码自检**：下面三条命令都要通过，参考答案自检不调用 API。
   ```powershell
   git pull
   python -m pytest tests -q
   python src/repair.py --dataset classeval --all-tests --init external/CangjieBench/CangjieBench/ClassEval_Cangjie.jsonl --rounds 0 -o results/try/ce_ref_alltests.jsonl
   ```
   - 第二条应输出 `36 passed`。
   - 第三条结束时，打印的 summary 里 `pass@1_by_round` 应为 `[97.62]`，即 82/84。
4. **看一遍要跑的命令**：
   ```powershell
   python src/run_matrix.py --dry-run
   ```

## 三、试跑（每组 10 题，约 1 小时）

```powershell
python src/run_matrix.py --pilot -p 2
```

结果写到 `results/stage3/pilot/`，不会和正式结果混在一起。跑完后脚本会自动做检查，所有组都应显示 `[正常]`。下列情况要**先停下来，联系项目负责人**：

- 有组显示 `[未完成]` 或 `[问题]`；
- 日志里频繁出现 `[llm] ... retry`，说明遇到了限流或网络问题；
- DeepSeek 或 Doubao 的日志里出现"回退到 1.0"，说明模型拒绝了 0.3 的温度。

## 四、正式运行

**三个模型可以同时跑**。各开一个终端，分别执行下面一行。三者写的文件互不重叠：

```powershell
python src/run_matrix.py -p 3 -j 6 --only doubao      # 终端 1
python src/run_matrix.py -p 3 -j 6 --only ds_v41f     # 终端 2
python src/run_matrix.py -p 2 -j 4 --only kimik31p    # 终端 3
```

- `-p` 是同时跑几组，`-j` 是每组内部同时跑几题。一个终端里同时在跑的请求数约等于 `p × j`。
- **耗时**：主要花在等待 API 返回上。按试跑实测，每次调用的耗时大约是：Doubao 10 秒，Kimi 45 秒，DeepSeek 在 ClassEval 上 2 分钟。按上面的并发、且不被限流，墙钟时间约 5–6 小时，瓶颈在 DeepSeek 的 ClassEval。如果按 `-p 2 -j 4` 让三个模型依次跑，总共要一天以上。
- **并发上限**：三个终端合计同时在跑的请求数不要超过约 40。这台机器有 16 核，ClassEval 每轮约编译 5 次，并发太高会让编译排队。编译超过 60 秒会被判为 `timeout` 失败，从而污染结果。
- **何时降并发**：
  - 日志里频繁出现 `retry`，说明被限流了；
  - 日志里 `timeout` 明显比试跑时多，说明机器过载了。

  出现任一情况，就停掉该终端（Ctrl+C），把 `-p` 降到 1–2 或把 `-j` 降到 4，再用同一条命令续跑。
- **中断后续跑**：直接重跑同一条命令。已完成的组会自动跳过，跑了一半的组从断点继续，不会重复计费。
- 运行日志在 `results/stage3/logs/<组名>.log`。
- 一组只有在 summary 中 `n` 等于题数（HumanEval 164，ClassEval 84）且 `errors = 0` 时才算完成。

## 五、跑完后的检查

```powershell
python src/run_matrix.py --check
```

所有组都应为 `[正常]`。检查项包括：

1. 题数完整，且 `errors = 0`；
2. 实际 temperature 等于设定值；
3. 修复组的第 0 轮判定和共享第 0 轮文件逐题一致（只给编译错误的组不检查这一项）。

如果有 `[问题]`，**不要删除任何文件**，把检查输出原样发给项目负责人。

- 跑完后告诉项目负责人，由负责人统计、更新报告，并统一提交。**运行实验的作者不需要自己提交。**

## 七、注意事项

- 跑实验期间不要修改 `src/` 下的代码。
- 不要删除或移动 `results/stage3/r0/` 下的第 0 轮文件，所有修复组都依赖它们。
- 可以同时运行多个 `run_matrix.py`，但它们的 `--only` 选中的组不能重叠，否则会同时写同一批文件。上面按模型分的三条命令互不重叠。不带 `--only` 的命令会包含所有组，不要和别的命令同时运行。
